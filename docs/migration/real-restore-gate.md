GitHub Actions применяется исключительно для фиктивных записей. **Ничего из рабочих данных, фотографий и ключей в GitHub не выгружать.**

На 19 ноября 2026 года в исходной облачной базе зарегистрированы 123 таблицы в `public`, 3 пользователя, 3 приватных хранилища и 44 файла. Есть 3 зашифрованные записи Vault и 4 активных SQL cron. ## Подготовка отдельного сервера (системный администратор)

1. Выделить новый чистый Linux-сервер для теста. На рабочую ПАНДУ не устанавливать второй стек поверх текущего. Установка: подготовленный `infra/supabase/prepare.sh`, PostgreSQL 17, HTTPS отдельно.
2. Запретить доступ извне к PostgreSQL 5432, внутреннему Supabase 8000 и веб-контейнеру 3000. Временно подключаться только через локальную консоль, а не открывать базу в интернет.
3. **До теста** отключить локальные задания Supabase pg_cron и самостоятельный планировщик, заблокировать исходящие запросы к маркетплейсам и Vercel из тестовой сети. Отключать старые задания в рабочей облачной базе не требуется.
4. Защищённым средством скопировать из действующего облака три SQL-файла по официальной процедуре Supabase CLI: `roles.sql`, `schema.sql`, `data.sql`. Их создавать и хранить **только в зашифрованном каталоге отдельного сервера**. Не загружать в репозиторий, чаты, файлы CI и сторонние сервисы. Не экспортировать старые `storage.objects`, `vault.secrets` и `cron.job`: первые будут созданы при переносе фотографий, секреты потребуют нового шифрования, а старые задания могут обращаться к Vercel.
5. Перед восстановлением проверить `sudo chmod 600 /srv/panda/restore-private/{roles,schema,data}.sql` и доступ root к каталогу с правами 0700. Использовать `scripts/storage-dump-preflight.mjs` для проверки `data.sql`, затем `infra/migration/restore-platform-test.sh` для восстановления только в полностью пустую локальную базу. Скрипт требует отдельного `PGSERVICEFILE` с правами 0600, подтверждения тестового назначения, выключенного планировщика и ожидаемых чисел таблиц/пользователей. **Автоматически не удаляет** никакую существующую базу. Повторно проверяет пустоту целевой БД внутри транзакции, импортирует и **до COMMIT** сверяет число таблиц/сотрудников и отсутствие старых Storage/Vault/cron записей. Несовпадение откатывает импорт. Диагностика SQL-ошибки хранится в закрытом файле `.restore-result.*` с правами 0600; не выводите его в CI или чат. При ошибке не повторяйте импорт, пока не разобрана причина и не проверено состояние БД.
6. В локальный конфигурационный файл rclone, доступный только root, внести S3-учётные записи действующего облака и тестового сервера. Использовать `infra/migration/copy-verify-private-storage.sh`, который переносит строго `avatars`, `ved-commercial-offers`, `ved-product-photos` и скачивает файлы с обоих концов для сравнения содержимого. На сегодня общее количество файлов — 44. Прямая запись обычных скачанных файлов в `volumes/storage` запрещена по официальным правилам Supabase.
7. Через раздел администрирования новой ПАНДЫ повторно ввести ключи маркетплейсов в **новый** Vault. Значения не пересылать в чат. Сверить наличие защищённых значений и возможность выполнять безопасную проверку подключения.
8. Проверить авторизацию всех 3 сотрудников, ограничение ролей, 123 таблицы и контрольные отпечатки схемы (`infra/migration/schema-fingerprint.sql`), реальные файлы и подписанные ссылки, финансовые итоги, закуп, ВЭД и Excel. Показатели не должны расходиться с зафиксированным на момент копирования источником. Для источника со продолжающимися записями обязательно учитывать разницу дат и времени.
9. Ни при каких условиях не запускать тестовый планировщик с рабочими ключами маркетплейсов до утверждённого переключения. Старую систему сохраняем для отката.

## Запуск на отдельном сервере

```bash
# Пример без настоящих паролей. Все файлы и доступы готовятся локально.
sudo env \
  PGSERVICEFILE=/root/.pg_service.conf \
  PANDA_TARGET_PGSERVICE=panda_test \
  PANDA_TARGET_DISPOSABLE=CONFIRMED_EMPTY_TEST_DATABASE \
  PANDA_SCHEDULER_DISABLED=YES \
  PANDA_TEST_DUMP_DIR=/srv/panda/restore-private \
  PANDA_EXPECT_AUTH_USERS=3 \
  PANDA_EXPECT_TABLES=123 \
  bash /srv/panda/app/infra/migration/restore-platform-test.sh

sudo env \
  RCLONE_CONFIG=/root/.config/rclone/rclone.conf \
  PANDA_SOURCE_REMOTE=platform \
  PANDA_TARGET_REMOTE=self-hosted \
  PANDA_TARGET_DISPOSABLE=CONFIRMED_EMPTY_TEST_DATABASE \
  PANDA_SCHEDULER_DISABLED=YES \
  bash /srv/panda/app/infra/migration/copy-verify-private-storage.sh
```

Примерные числа выше нужно заменить на свежие показатели источника. В `/root/.pg_service.conf` должно быть отдельное соединение `[panda_test]` с полями `host=127.0.0.1`, `port=15432` (временный прямой туннель профиля `restore`), `dbname=postgres`, `user=supabase_admin`, `passfile=/root/.pgpass`. Оба файла должны принадлежать root и иметь режим 0600. Прямое указание `hostaddr`, удалённого адреса и libpq-переменных, переопределяющих цель, запрещено. При Docker NAT сервер внутри контейнера видит свой внутренний адрес: безопасный **клиентский** адрес проверяется по `PGSERVICEFILE`, а не по `inet_server_addr()`. Никаких паролей в аргументах команд.

## Защитные ограничения

- Скрипты не являются командой `docker compose down -v` и не удаляют рабочие тома.
- Если целевая база не пустая, импорт отменяется. Отсутствие `cron.job` в новой Supabase допустимо; если таблица существует и содержит хотя бы одну запись, восстановление блокируется. Запрещено создавать `cron.job` вручную ради предварительной проверки.
- Если дамп содержит старые задания и метаданные фотографий, импорт отменяется.
- Если целевой S3 уже содержит файлы или указывает на неправильный адрес, копирование отменяется.
- Если содержимое любого файла отличается, тест не проходит.
- Для обновления рабочей системы позднее необходим отдельный план остановки записей, контрольного повторного переноса и отката.
- **Никаких реальных данных сейчас не переносилось**, поскольку отсутствует защищённая тестовая установка, к которой есть доступ для записи.
