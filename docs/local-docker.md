# Локальный Docker: единый запуск ПАНДЫ

Это **отдельная локальная конфигурация**, не замена действующему Vercel/Supabase и не автоматическая миграция данных. Используется официальный self-hosted Supabase, закреплённый в `infra/supabase/prepare.sh`, Next.js и локальный Caddy-прокси.

## Требования и первая инициализация

Linux с Docker Engine, Docker Compose **2.24.4+**, Git, OpenSSL, Bash, util-linux (`flock`) и свободным местом для образов/БД. Для генерации новых Auth-ключей нужен Node.js >=16 на хосте **либо** доступный Docker daemon.

**Одна команда для первого и последующих запусков** из корня проекта:

```bash
bash infra/local/start.sh
```

При первой установке скрипт однократно создаёт секреты и конфигурацию, затем выполняет `docker compose up -d --build --wait`. На следующих запусках использует существующие ключи без перегенерации. Если обнаружена частичная инициализация, недоступен Docker, изменены права на секреты или включён планировщик, он останавливается, не перезаписывая данные. Это удобная оболочка над стандартным Compose, а не отдельный менеджер контейнеров.

Для отдельной проверки конфигурации без запуска контейнеров:

```bash
bash infra/local/start.sh --check
```

Можно использовать и прямой Docker Compose, если первоначальная инициализация уже завершена:

```bash
docker compose -f compose.local.yaml --env-file .env.docker up -d --build --wait
docker compose -f compose.local.yaml --env-file .env.docker ps
```

Страница входа: http://localhost:8080/login. Запросы браузера к `/auth/v1`, `/rest/v1`, `/storage/v1`, `/realtime/v1` и `/functions/v1` проксируются внутри Docker; Supabase Studio наружу не публикуется. Прямые порты Supabase и Next.js остаются на loopback. Scheduler **не запускается**: запускать задания на свежей или тестовой базе нельзя.

Для штатной инициализации PostgreSQL SQL-файлы поставки должны быть доступны внутренним пользователям контейнеров; ключи и `.env` при этом остаются закрытыми. Healthcheck БД ожидает назначения паролей служебным ролям.

`init.sh` (вручную или через `start.sh`) запускается **один раз** и отказывает в перезаписи существующих `.env.docker`, `.panda-local/supabase` или `.panda-local/secrets`. Он получает официальные файлы Supabase, создаёт новые ключи и закрытые конфигурационные файлы, выключает открытую регистрацию и подключает общую сеть `panda_shared`. Изменения секретов нельзя делать повторным запуском инициализатора, иначе существующие сессии и зашифрованные данные могут стать недоступными.

## Важно: пустой Supabase ≠ рабочие бизнес-данные

Первый запуск создаёт **инфраструктуру**, но не может из воздуха создать существующую бизнес-схему, пользователей и фотографии. Исходные SQL-миграции в `supabase/migrations` инкрементальные и не являются подтверждённым полным baseline. До авторизации и проверки бизнес-модулей необходима отдельная защищённая процедура восстановления baseline/данных по `docs/migration/real-restore-gate.md`. Не направляйте тестовые задачи на производственные API и не включайте планировщик до cutover. Запуск `docker compose up` **не** восстанавливает и не удаляет БД.

## Повторные действия

```bash
docker compose -f compose.local.yaml --env-file .env.docker up -d --build
docker compose -f compose.local.yaml --env-file .env.docker logs -f panda-web
docker compose -f compose.local.yaml --env-file .env.docker down
```

**Не применяйте `down -v` или `reset.sh` к данным, которые нужно сохранить.** Образы обновляются через сборку, данные PostgreSQL/Storage находятся в игнорируемом каталоге `.panda-local/supabase/volumes`, служебные Docker volumes и ключи — отдельно. Существующие файлы `.panda-local` и `.env.docker` никогда не коммитятся.

## Доступ с другого компьютера

По умолчанию HTTP открыт только на `127.0.0.1:8080`; это безопасно для тестов через SSH-туннель. Для сервера в LAN/интернете не открывайте без TLS адрес `0.0.0.0:8080` с авторизацией и токенами. Настройте HTTPS reverse-proxy на сервере и укажите при **первой** инициализации `PANDA_PUBLIC_ORIGIN=https://имя-домена`. Публичный URL встраивается в образ Next.js при сборке, а Supabase Auth использует его для обратных ссылок; изменение адреса после инициализации требует согласованного редактирования обоих env-файлов и пересборки. Прокси должен направлять эти же разрешённые пути к локальному Caddy, не открывая Studio и порты БД.

## Проверка после запуска

```bash
docker compose -f compose.local.yaml --env-file .env.docker config --quiet
docker compose -f compose.local.yaml --env-file .env.docker ps
curl -fsSI http://127.0.0.1:8080/login
# Только чтение структуры локальной БД. Для пустого Supabase код выхода 78.
bash infra/local/check-business-schema.sh
```

HTTP 200/3xx страницы входа означает только запуск Next.js и прокси, **не** проверку Auth, RLS, Storage, Vault, миграции, фоновых задач или восстановления данных. Для настоящего переноса следуйте отдельным сценариям и контрольным спискам в `docs/migration/`.

## Проверка бизнес-схемы и сохранности данных

Команда `bash infra/local/check-business-schema.sh` только читает агрегаты PostgreSQL: число таблиц, RLS, наличие нескольких критических таблиц, число пользователей Auth и Storage buckets. **На новой пустой установке она специально возвращает код 78**: это защита от ложного заявления о готовности ПАНДЫ после `docker compose up`. Она не создаёт таблиц, не импортирует миграции, не удаляет пользователей и не выводит значения секретов.

После согласованного защищённого импорта полного baseline можно дополнительно указать `PANDA_EXPECT_PUBLIC_TABLES=<актуальное_число>` по свежей инвентаризации источника. Проверка структуры — **не** доказательство совпадения схем, разрешений или данных: отдельно сравниваются отпечатки `infra/migration/schema-fingerprint.sql`, сотрудники, роли, три приватных хранилища и бизнес-функции. Нельзя использовать число 123 из снимка 19 ноября как постоянную норму.

В GitHub Actions применяется только синтетическая база: создаются тестовый пользователь и приватный PNG-файл, выполняется `docker compose stop`, затем `up -d --wait` **без удаления volumes**, и проверяются вход пользователя, байты файла, подписанная ссылка и запрет публичного чтения. Это подтверждает сохранность данных на тесте при остановке/перезапуске; не является полной проверкой backup/restore действующего сервера.

**Нельзя** получать реальный `schema.sql` или `data.sql` в GitHub Actions. Полный baseline существует только как защищённый экспорт исходного Supabase, который должен восстанавливаться на отдельном сервере по `docs/migration/real-restore-gate.md` с явным контролем цели и остановленными заданиями.

## Защищённый импорт полного baseline

Экспорт Supabase CLI (`roles.sql`, `schema.sql`, `data.sql`) с реальными записями должен оставаться вне GitHub: подготовьте на отдельном сервере root-каталог 0700 и три root-файла 0600. Импорт выполняется отдельно, **не при каждом `docker compose up`**, через `infra/migration/restore-platform-test.sh` по инструкции `docs/migration/real-restore-gate.md` и только после согласования тестовой цели. Внутри одной транзакции проверяется, что цель пустая, и соответствие результата счётчикам источника до COMMIT. Это не заменяет перенос Storage через S3, безопасное повторное создание Vault-секретов и полное тестирование бизнес-сценариев.

### Временный прямой доступ к PostgreSQL для восстановления

Обычная команда `docker compose up` **не запускает** профиль `restore` и не публикует PostgreSQL напрямую. Порт `127.0.0.1:5432` в поставке Supabase относится к Supavisor; **не используйте его для восстановления полного SQL**. На время разрешённого импорта запустите мост:

```bash
docker compose -f compose.local.yaml --env-file .env.docker --profile restore up -d panda-db-tunnel
# Далее: защищённый импорт по docs/migration/real-restore-gate.md
# В закрытом PGSERVICEFILE укажите host=127.0.0.1, port=15432.
docker compose -f compose.local.yaml --env-file .env.docker --profile restore stop panda-db-tunnel
docker compose -f compose.local.yaml --env-file .env.docker --profile restore rm -f panda-db-tunnel
```

Мост только пересылает TCP в контейнер `db:5432`; PostgreSQL по-прежнему проверяет пароль. Храните `PGSERVICEFILE` и `passfile` вне репозитория с правами 0600. Не оставляйте этот профиль включённым после импорта, не открывайте его порт в LAN и не используйте `down -v` ради остановки моста.
